# Устройство мира и как сделать перерисовку дешёвой

Документ отвечает на один вопрос: **что нужно изменить сейчас, чтобы позже заменить
графику мира без переписывания кода.**

Короткий ответ: рантайм уже почти готов к такой замене, а вот пайплайн генерации —
нет, и именно он является точкой блокировки. Инвертировать его нужно **до** расстановки
миссии, иначе работа по расстановке обесценится.

---

## 1. Как устроено сейчас

Три слоя, из которых только первый знает об оригинале.

```
assets/reference/original/maps/Saboteur2_speccy.png     ← рип, в .gitignore
        │
        │   tools/saboteur_rip/build_s2_world.py
        │   839 строк классификации по цветам ZX
        ▼
   ┌────────────────────────┬──────────────────────────────────────────┐
   │ assets/world/*.png     │ assets/world/s2_collision.json           │
   │ saboteur2_world.png    │ solids / ladders / lifts / bookcases     │
   │ saboteur2_fg.png       │ spawn / size / screen / cell / scale     │
   │ s2_lift.png            │                                          │
   └────────────────────────┴──────────────────────────────────────────┘
        │                                    │
        │   scripts/levels/level_01.gd::_load_original_world()
        ▼                                    ▼
   Sprite2D "OriginalMap" z=-20        StaticBody2D "Solids"  — 4643 CollisionShape2D
   Sprite2D "Foreground"  z=12         Node2D "Ladders"       — 67 Area2D
                                       Node2D "Lifts"         — 4 AnimatableBody2D
```

### 1.1. Как объявлены объекты мира

Весь мир — это один JSON с числами. Схема `s2_collision.json`:

| Ключ | Тип | Кол-во | Смысл |
|---|---|---|---|
| `scale` | int | — | Множитель мозаики → мировые пиксели (`2`) |
| `cell` | int | — | Размер символьной ячейки ZX (`8`) |
| `screen` | `[w, h]` | — | Размер экрана Spectrum (`[256, 192]`) — задаёт зум камеры и мёртвую зону |
| `size` | `[w, h]` | — | Размер мозаики в пикселях (`[8192, 4608]`) |
| `spawn` | `[x, y]` | — | Точка появления в мировых координатах |
| `solids` | `[x, y, w, h]` | 4643 | Прямоугольники коллизий, слой 4 |
| `ladders` | `[x, y, w, h]` | 67 | Зоны лестниц, `Area2D` на слое 16 |
| `lifts` | `{x, y, w, h, top, bottom}` | 4 | Кабина и границы шахты |
| `bookcases` | `[x, y, w, h]` | 9 | Только для шейдера обводки, не коллизия |

`level_01.gd` собирает из этого узлы процедурно: `_add_rect_shape()` для солидов,
цикл с `Area2D` для лестниц, `_add_lifts()` для лифтов. Прямоугольники солидов
получаются жадной склейкой ячеек (`greedy_rects()`), поэтому их 4643, а не 200 тысяч.

Зоны лестниц дополнительно расширяются на ±4 пикселя (`[x - 4, y, w + 8, h]`)
и отбрасываются, если короче 24 пикселей, — чтобы окна и обои рядом с шахтой
не становились лазаемыми.

### 1.2. Главное: рантайм ничего не знает про Saboteur II

Это ключевой факт, и он в пользу твоего плана.

`player.gd`, `lift.gd`, `guard.gd` не содержат ни одной ссылки на исходный материал.
`level_01.gd` читает JSON с числами и текстуру по пути. Замени содержимое JSON и PNG —
и код продолжит работать как есть. С точки зрения игровой логики мир уже **данные**,
а не захардкоженный уровень.

Поэтому «перерисовать мир» **не требует** правок в игровом коде. Проблема в другом месте.

## 2. Где настоящая связанность

### 2.1. Генератор — это классификатор, а не формат уровня

`build_s2_world.py` не читает описание уровня. Он **восстанавливает геометрию
из пикселей** по цветам ZX-палитры:

```python
def _col(r, g, b):        # RGB → буква краски ZX: k b g c r y w m
...
red_brick = counts["r"] >= 10 and counts["k"] >= 4
speckled_earth = counts["k"] >= 48 and 1 <= counts["b"] <= 8 and ...
black_wall = counts["k"] >= 40 and counts["g"] < 20
```

Лестницы распознаются по точному пиксельному узору символа
(`_is_green_rail_tile`, `_is_x_lattice_tile`), книжные шкафы — по трём захардкоженным
битмапам полки в `PLANK_TILES`, кабины лифтов — по бирюзовому цвету
(`cell_is_lift_car`), ящики — по жёлтому на чёрном (`cell_is_crate`).

Тип помещения определяется подсчётом синих и зелёных пикселей на экран:

```python
if sky / n > 0.55:        biomes.append("sky")
elif grn / n > 0.12:      biomes.append("interior")
else:                     biomes.append("cave")
```

**Любая перерисовка ломает все эти правила разом.** Не рантайм — генератор.
Нарисуй стену в другой палитре, и `counts["r"] >= 10` перестанет срабатывать.

### 2.2. Коллизия не является функцией внешнего вида

Это тонкий момент, который легко упустить при переходе на тайлсет.

Одинаково выглядящие чёрные ячейки получают разную проходимость в зависимости
от контекста:

- `fill_cave_earth()` — заливка от достижимого воздуха; чёрная масса в пещере,
  до которой нельзя добраться сверху, становится камнем
- `thicken_floors(solid, 3)` — полы наращиваются вниз на три ячейки, чтобы быстрое
  падение не проваливалось сквозь 8 пикселей кирпича
- `punch_ladder_shafts()` / `cap_ladder_hatches()` — шахта под люком открывается,
  но крышка остаётся проходимой сверху
- в биоме `interior` чёрная стена солидна только у краёв экрана
  (`cx < 3 or cx >= cw - 3 or cy >= ch - 3`), в `cave` — почти везде

Вывод: **нельзя просто перекрасить картинку и перезапустить скрипт.** И нельзя
привязать коллизию к внешнему виду тайла — две визуально одинаковые ячейки должны
вести себя по-разному.

### 2.3. Нет редактируемого источника правды

Уровень существует **только** в виде пикселей чужой игры. Чтобы подвинуть платформу,
нужно отредактировать мозаику 8192×4608 и прогнать классификатор заново.

Отсюда же и мелкий симптом: `find_spawn()` в генераторе написан, но не вызывается —
`main()` использует литерал `spawn = [4480, 1584]`, подобранный вручную. Так и будет
происходить с каждым параметром, который классификатор не смог угадать.

## 3. Как это обычно делают

Во всех движках и редакторах для 2D-платформеров работает один принцип:
**разделять «как тайл выглядит» и «как тайл себя ведёт»**, а источником правды
держать редактируемую карту, а не картинку.

Типичные варианты:

- **TileMap самого движка.** Уровень рисуется в редакторе Godot. Коллизия — свойство
  тайла в `TileSet` (physics layers), дополнительные признаки вроде «лестница»
  или «шип» — через custom data layers. Коллизии не описываются вручную нигде:
  движок собирает их из тайлов. Самый распространённый вариант.
- **Tiled (`.tmx`) + импортёр.** То же самое, но карта живёт во внешнем редакторе.
  Удобно, когда уровни делает отдельный человек.
- **LDtk.** Современный редактор для инди-2D: слои сущностей, автотайлинг,
  аккуратный JSON на выходе.

Общее свойство всех трёх: **перерисовка игры = замена атласа при сохранении
идентификаторов тайлов и самой карты.** Ни карта, ни коллизии, ни расстановка объектов
при этом не трогаются. Это ровно то свойство, которое тебе нужно.

Объекты (лифты, точка спавна, позже предметы и охрана) в такой схеме не входят
в тайловую сетку — они лежат отдельным слоем сущностей или обычными нодами в сцене.

## 4. Что делать в этом проекте

### 4.1. Инвертировать пайплайн один раз, сейчас

Прогнать `build_s2_world.py` **последний раз**, но заставить его выдать не списки
прямоугольников, а **тайловую карту**. После этого исходный рип не читается больше
никогда, а источником правды становится карта, редактируемая в Godot.

Насколько это тяжело: скрипт уже проходит по всем ячейкам сетки и уже классифицирует
каждую. Нужно добавить сбор уникальных ячеек в словарь и выгрузку двух слоёв вместо
списков ректов. Вся сложная логика (`fill_cave_earth`, `thicken_floors`,
`punch_ladder_shafts`) остаётся как есть — меняется только форма результата.

### 4.2. Два слоя, а не один

Из-за пункта 2.2 привязывать коллизию к внешнему виду тайла нельзя. Поэтому:

| Слой | Тайлсет | Физика | Видимость |
|---|---|---|---|
| `Visual` | атлас уникальных ячеек (~2000 тайлов) | нет | да |
| `Collision` | 3–4 семантических тайла: `solid`, `ladder`, `oneway` | да | нет |

Это и есть точка развязки. **Перерисовка трогает только атлас слоя `Visual`.
Слой `Collision` не меняется вообще** — ни одной ячейки, ни одной строки кода.

Лестницы при этом перестают быть 67 отдельными `Area2D` и становятся тайлами
с признаком — но это опционально, текущая схема с `Area2D` тоже рабочая и её можно
оставить, чтобы не трогать выверенную логику лазанья в `player.gd`.

### 4.3. Сколько на самом деле придётся перерисовать

Я посчитал мозаику. Из 589 824 ячеек карты:

| Метрика | Значение |
|---|---|
| Уникальных ячеек с учётом цвета | 2968 |
| Уникальных **форм** без учёта цвета | 1981 |
| Форм, покрывающих 90% карты | 8 |
| Форм, покрывающих **99% карты** | **295** |

То есть перерисовка мира — это не 37 мегапикселей, а **около 300 картинок 8×8**,
после чего 99% карты выглядит по-новому. Оставшийся процент — редкие детали,
которые можно добивать по мере необходимости.

Для сравнения, сейчас «перерисовать» означает «переписать 839 строк классификатора
под новую палитру и заново выверить проходимость всей карты».

### 4.4. Побочные выигрыши

Инверсия пайплайна закрывает сразу несколько пунктов
[плана устранения замечаний](remediation_plan.md):

- **1.1 (память).** Атлас из 2968 ячеек — примерно 440×440 пикселей, 0.74 МБ RGBA8
  против 144 МБ на текстуру. Вопрос мобильной памяти закрывается полностью.
- **0.2 (сжатие).** Атлас такого размера можно держать Lossless, и развилка
  «блочное сжатие портит пиксель-арт против 288 МБ в VRAM» исчезает.
- **2.3 (миссия).** Появляется редактируемая карта, по которой можно расставлять
  цели прямо в редакторе, а не подбирать координаты вслепую.

## 5. Порядок работ с учётом юридической части

Это меняет очерёдность в [плане](remediation_plan.md): пункт 1.1 нужно делать
**до** пункта 2.1, а не после.

```
0. Этап 0 плана — вернуть проект в собираемое состояние
1. Инверсия пайплайна: рип → тайлсет + карта (пункт 1.1)
2. Расстановка миссии по редактируемой карте (пункт 2.1)
3. Постепенная замена атласа своей графикой — в любой момент, без правок кода
```

Смысл такого порядка: расстановка миссии привязывается к координатам мира. Если
сначала расставить цели, а потом менять представление мира, работу придётся
переделывать. После инверсии координаты фиксируются и переживают любую перерисовку.

Что остаётся от рипа после шага 1:

- `Saboteur2_speccy.png` — не читается больше никогда, остаётся вне репозитория
- атлас тайлсета — **один локализованный файл**, который и подлежит замене
- планировка уровня (сетка тайлов) — отдельный вопрос, см. ниже

Про планировку: с инженерной точки зрения она отделена от графики и живёт в карте,
которую можно редактировать в редакторе Godot. Насколько её нужно менять — вопрос
не технический, и решать его стоит с юридической консультацией, если проект пойдёт
в публикацию. Важно другое: **после инверсии и перерисовка, и перепланировка
становятся работой в редакторе, а не переписыванием кода.**

## 6. Что заодно стоит развязать в `level_01.gd`

Мелочи, которые сейчас привязаны к конкретному арту и всплывут при замене:

- `Vector2(48.0, 56.0)` — размер спрайта игрока захардкожен дважды,
  в `_player_center()` и `_update_ink_outline()`. Брать из `AnimatedSprite2D`.
- `_bookcases` + `zx_ink_outline.gdshader` — обводка нужна только потому, что
  внутренность шкафа в оригинале такая же чёрная, как Нина. Это артефакт
  цветового клэша ZX. С новой графикой, скорее всего, не понадобится; схема
  уже управляется данными (список ректов), поэтому при пустом списке просто
  выключится сама.
- `LETTERBOX_PX = 160` и зум камеры `720.0 / (_screen.y * _scale)` привязаны
  к viewport 1280×720. При смене разрешения разъедутся.
- `spawn` в генераторе задан литералом, а написанный `find_spawn()` не вызывается.
  После инверсии точка спавна должна стать обычной сущностью на карте.
