# Аудит проекта saboteur-92

Дата: 2026-09-06. Ревизия: `e14d8c8`. Проверялось на Godot `4.6.stable.official.89cea1439`.

Все утверждения ниже подтверждены запуском проекта, сборкой экспорта и рантайм-пробами,
а не только чтением кода. Сырые логи — в разделе [Как это проверялось](#как-это-проверялось).

---

## 1. Резюме

Проект — это **технически сильный прототип управления персонажем внутри карты, вырванной
из оригинального Saboteur II**, а не игра. Ядро движения (лестницы, лифты, удары, камера
в стиле flip-screen) проработано аккуратно и с уважением к оригиналу. Всё остальное —
миссия, сборка, инфраструктура — либо отключено, либо не работает.

Главный вывод: **собранная версия игры неработоспособна**. Причём ломается она молча —
в редакторе всё выглядит правильно, а в `.pck`/APK мир исчезает целиком. Это не мелкий
баг, а следствие архитектурного решения грузить карту через `Image.load()` из `res://`.

| Область | Оценка | Комментарий |
|---|---|---|
| Механика движения | Хорошо | Лестницы, лифты, удары, камера — продумано и подогнано под оригинал |
| Геометрия мира | Дыры | 8950 ячеек грунта без коллизии — игрок проваливается сквозь породу |
| Игровой цикл | Отсутствует | Все цели миссии отключены в рантайме |
| Сборка / экспорт | Сломано | Мир не рендерится в собранной игре; Android-экспорт падает |
| CI | Не работает | Ни одного запуска за всю историю репозитория |
| Гигиена репозитория | Слабо | Битые UID, `.pyc` в git, абсолютные Windows-пути |
| Мобильная готовность | Низкая | Нет половины управления, ~288 МБ текстур в VRAM |
| Юридическая чистота | Риск | Рипы оригинала коммитятся и попадают в APK, лицензии нет |

## 2. Блокеры

### 2.1. Автозагрузка ссылается на файл, которого нет в репозитории

`project.godot` объявляет автозагрузку `McpBridge="*res://mcp_bridge.gd"`, а `.gitignore`
явно исключает `mcp_bridge.gd`. То есть файл не может существовать ни у кого, кроме автора.
Любой запуск — в редакторе, headless и в собранной игре — начинается с трёх ошибок движка.

Симптоматично, что коммиты `fc581f2` и `6741401` уже удаляли эту ссылку, а потом она
вернулась. Значит, локальный dev-инструментарий утекает в общий конфиг регулярно.

Что делать: убрать `McpBridge` из `project.godot`. Если мост нужен для разработки —
оформить его плагином в `addons/` и подключать через `EditorPlugin`, а не автозагрузкой
в игровом конфиге.

### 2.2. В собранной игре не видно мира — вообще

`scripts/levels/level_01.gd` грузит фон, передний план и спрайт лифта так:

```gdscript
var img := Image.new()
if img.load(path) != OK:      # path == "res://assets/world/saboteur2_world.png"
    push_error("Could not load %s" % path)
```

`Image.load()` читает файл с диска. В экспортированной сборке исходных `.png` нет — есть
только импортированные `.ctex` внутри `.pck`. Движок предупреждает об этом прямым текстом
(`"Loaded resource as image file, this will not work on export"`), и предупреждение
игнорируется.

Проверено на реальном экспорте — те же пути, тот же коммит:

```
ПАКЕТ:   res://assets/world/saboteur2_world.png | file_exists=false | Image.load=FAIL(7)
ИСХОДНИК: res://assets/world/saboteur2_world.png | file_exists=true  | Image.load=OK
```

Хуже всего то, что **отказ молчаливый**: `_add_map_sprite()` проверяет
`FileAccess.file_exists()` и просто выходит без единого сообщения. Коллизии при этом
грузятся нормально (JSON попадает в пакет), поэтому игрок стоит на невидимом полу
посреди серой пустоты и всё выглядит «как будто запустилось».

Что делать: заменить `Image.load()` на `load()`/`preload()` ресурса, а `FileAccess.file_exists()`
на `ResourceLoader.exists()`. Это правка на несколько строк, и она же включит сжатие
текстур при импорте (см. 3.1).

### 2.3. Игрового цикла нет: миссия отключена целиком

`level_01.tscn` содержит старый прототипный уровень (640×256) с охраной, ключом,
документом, бомбой, целью саботажа и выходом. Но `_ready()` сначала затирает `World`
и подгружает вырванную карту Saboteur II, а затем вызывает `_hide_demo_entities()`,
который гасит и отключает **все** объекты миссии.

Рантайм-проба через секунду после загрузки `main.tscn`:

```
Guards          : visible=false  process_mode=DISABLED  children=3
Items           : visible=false  process_mode=DISABLED  children=3
SabotageTarget  : visible=false  process_mode=DISABLED  children=2
ExitZone        : visible=false  process_mode=DISABLED  children=2
solids built from JSON : 4643      ladder areas : 67      lifts : 4
```

Практические следствия:

- `GameManager`, `pickup.gd`, `sabotage_target.gd`, `exit_zone.gd`, `guard.gd`
  и инвентарь в HUD — недостижимый код. Он компилируется, но никогда не выполняется.
- Условия победы не существует. Умереть можно только упав за границу мира
  (`level_01.gd::_process`).
- `README` описывает mission flow из пяти шагов, которого в игре нет.
- `scripts/demo/mission_demo.gd` (`--demo`) оперирует координатами старого уровня
  (`LADDER_X := 592.0`, `GROUND_Y := 184.0`), тогда как спавн теперь `(4480, 1584)`,
  а цели отключены. Автопилот не может завершиться — он устарел и вводит в заблуждение.

Это главное расхождение между тем, чем проект себя объявляет, и тем, чем он является.
Ничего «сломанного» тут нет — просто миссию не перенесли на новую карту. Но пока этого
не сделано, `GameManager` и всё под `scenes/items/` стоит считать не рабочей системой,
а заготовкой.

### 2.4. Ни один запуск CI не состоялся

`.github/workflows/android-export.yml` триггерится на ветку `main`. Ветка по умолчанию —
`master`. `gh run list` возвращает пустоту: workflow не выполнялся ни разу.

### 2.5. Даже с исправленным триггером Android-экспорт упадёт

Воспроизведение шага CI один в один:

```
$ godot --headless --path . --export-debug "Android" exports/saboteur92.apk
ERROR: Cannot export project with preset "Android" due to configuration errors:
Android build template not installed in the project. Install it from the Project menu.
...
ANDROID EXPORT EXIT=1
```

`export_presets.cfg` содержит `gradle_build/use_gradle_build=true`, то есть требует
установленного в проект gradle-шаблона. Workflow никогда не вызывает
`godot --install-android-build-template`, а `android/build/` в `.gitignore`.
Претензии к SDK/JDK шаги `setup-java` и `setup-android` частично снимут — отсутствие
build-шаблона не снимут.

Что делать: починить триггер на `master`, добавить установку build-шаблона перед
экспортом и явно передать Godot путь к Android SDK. И убедиться, что job падает при
ошибке экспорта, а не выкладывает пустой артефакт.

## 3. Серьёзные проблемы

### 3.1. Бюджет памяти для мобильной платформы превышен на порядок

`saboteur2_world.png` и `saboteur2_fg.png` — по 8192×4608. В PNG они весят по ~700 КБ
и ~170 КБ (спасибо палитре ZX), но в видеопамяти это два несжатых RGBA8-буфера
по 144 МБ — **288 МБ суммарно**. Плюс 8192 — это ровно предел `GL_MAX_TEXTURE_SIZE`
у заметной части мобильных GPU, то есть на части устройств текстура просто не создастся.

Ключевой момент: `Image.load()` + `ImageTexture.create_from_image()` **полностью обходят
импорт-пайплайн Godot**. Настройки `import_etc2_astc=true` в `project.godot` к этим
текстурам не применяются. Даже если исправить 2.2 переходом на `load()`, для карты такого
размера всё равно понадобится атлас или нарезка по экранам — оригинал ведь и так
устроен как сетка flip-screen'ов.

### 3.2. На телефоне недоступна половина управления

`touch_controls.tscn` содержит четыре кнопки: `◀`, `▶`, `JMP`, `HIT`. Кнопок «вверх»
и «вниз» нет, хотя `README` обещает `▲/▼`, а в мире 67 лестниц и 4 лифта.

Частично спасает костыль в `player.gd::_climb_axis()` — удержание `jump` на лестнице
трактуется как «вверх». Но `move_down` не эмулируется ничем, поэтому на сенсорном
управлении **невозможно спуститься по лестнице, присесть и опустить лифт**. Для проекта,
который позиционируется как мобильный ремейк, это дыра в основном цикле взаимодействия.

Сюда же: `input_devices/pointing/emulate_touch_from_mouse` не включён, поэтому
`TouchScreenButton` не реагируют на мышь и управление нельзя проверить на десктопе.

### 3.3. После Game Over игра запирается навсегда

`GameManager.state` переводится в `LOST`, но обратно в `PLAYING` не возвращается нигде.
`lives` не сбрасывается. `reload_current_scene`, `change_scene_to_*` и обработчика
`ui_accept` в проекте нет вообще. После трёх смертей `player._physics_process()` уходит
в ранний `return`, и остаётся только закрыть приложение. Экрана поражения/победы тоже нет —
только текст в `StatusLabel`.

### 3.4. Юридический риск

`tools/saboteur_rip/build_s2_world.py` строит игровой мир из
`assets/reference/original/maps/Saboteur2_speccy.png` — то есть напрямую из графики
оригинальной Saboteur II: Avenging Angel (Durell Software, 1987). `.gitignore` содержит
честный комментарий:

```
# Original game rips — dev reference only, do not ship
assets/reference/
```

Но производная от этих рипов — `assets/world/saboteur2_world.png` и `saboteur2_fg.png` —
закоммичена в репозиторий и попадает в APK. Намерение «не отгружать оригинал»
на практике не выполняется: отгружается ровно он, только перекодированный.

Дополнительно: файла `LICENSE` в репозитории нет, а `README` ограничивается фразой
«Game assets and code are part of the saboteur-92 project», которая ничего не определяет.

Это не блокер для личного прототипа, но становится блокером в момент публикации
в любом сторе. Решение — либо перерисовать мир по мотивам, либо оставить рип
исключительно как локальный референс и генерировать карту у разработчика, а не в git.

### 3.5. Грунт в помещениях не имеет коллизии — игрок проваливается сквозь него

Найдено по наводке от разработчика и подтверждено сверкой `s2_collision.json`
с `saboteur2_world.png`. Проверяется командой:

```bash
python tools/saboteur_rip/audit_collision.py
```

Чёрный грунт с редкими синими крапинами — сплошная порода, сквозь которую пройти
нельзя. В отгружаемых данных **8950 из 9266 таких ячеек (96.6%) не имеют коллизии**:

```
[грунт (speckled)] всего 34542, БЕЗ коллизии 8952 (25.9%)
    cave      всего   21010, дыр       0 (0.0%)
    interior  всего    9266, дыр    8950 (96.6%)
    sky       всего    4266, дыр       2 (0.0%)
```

Распределение по биомам указывает на причину напрямую. В `build_s2_world.py`
проходимость выбирается веткой по типу экрана:

```python
if biome == "sky":
    if counts["b"] >= 40:                                    pass
    elif red_brick or black_wall or speckled_earth:          solid[cy][cx] = 1
elif biome == "interior":
    if red_brick:                                            solid[cy][cx] = 1
    elif black_wall and (cx < 3 or cx >= cw - 3 or cy >= ch - 3):
                                                             solid[cy][cx] = 1
else:  # cave
    if red_brick or speckled_earth:                          solid[cy][cx] = 1
```

**В ветке `interior` проверки `speckled_earth` просто нет.** В `sky` и `cave` она
есть, и там дыр ноль. Одна пропущенная строка обнуляет грунт на всех экранах,
которые классификатор счёл помещениями.

Затронут 91 экран из 140 помещений. Хуже всего экран (25,7) — там коллизии нет
вообще ни у одной ячейки, игрок проваливается сквозь весь экран насквозь.

Симптом усиливается тем, что биом определяется на весь экран 256×192 сразу:

```python
if sky / n > 0.55:      "sky"
elif grn / n > 0.12:    "interior"
else:                   "cave"
```

Достаточно, чтобы в углу экрана оказалась комната с зелёными обоями, — и весь
экран, включая толщу грунта, помечается как `interior`, после чего правила
грунта для него отключаются целиком.

Заодно рядом видна вторая некорректность: условие `cx < 3 or cx >= cw - 3 or cy >= ch - 3`
в той же ветке использует размеры **всей карты** (1024×576 ячеек), а не экрана.
Под него попадает 6510 ячеек из 589 824 — внешняя рамка мира, а не стены комнаты.
Судя по замыслу, имелись в виду края экрана.

## 4. Качество кода

Общее впечатление: код **аккуратный и последовательный** — единый стиль, статическая
типизация почти везде, осмысленные имена, комментарии объясняют намерение
(«Original flips the same sprite every tile…»), а не пересказывают строчку. Проблемы
не в стиле, а в структуре.

### 4.1. `player.gd` — 676 строк и слишком много ответственностей

Один класс держит: платформер-движение, лазанье по лестницам с покадровым шагом,
езду на лифтах, три вида атак, анимацию, урон, регенерацию, i-frames и респавн.
Это самый сложный и самый ценный файл в проекте, и он же самый рискованный для правок.

Напрашивается выделение как минимум `LadderController` и `LiftRider` — тем более что
границы уже видны: методы лестниц не трогают ничего, кроме `on_ladder`, позиции
и `collision_mask`.

### 4.2. Четыре почти одинаковые функции запроса физики

`_ladder_overlaps()`, `_ladder_overlaps_at()`, `_ladder_at_world()` и `_ladder_probe()`
делают одно и то же с точностью до трансформа и формы. Каждая создаёт новый
`PhysicsShapeQueryParameters2D` (а две из них — ещё и новый `RectangleShape2D`).
`_ladder_overlaps()` вызывается каждый физический кадр, то есть проект аллоцирует объекты
в горячем цикле — на мобильном GC это заметно.

Сводится к одной функции с переиспользуемым `PhysicsShapeQueryParameters2D` в поле класса.

### 4.3. Магические числа вместо именованных слоёв

`project.godot` задаёт имена слоёв (`world`, `triggers`, …), но код оперирует битовыми
масками напрямую: маска мира `4` захардкожена в `player.gd` семь раз (строки 78, 330,
351, 504, 512, 536, 660), плюс `collision_layer = 4/16` в `level_01.gd`. Одна опечатка
в константе — и игрок молча проваливается сквозь мир.

Справедливости ради, маску лестниц код берёт правильно —
`q.collision_mask = ladder_detector.collision_mask`, из самой ноды. Тот же приём стоит
применить и к миру: вынести маски в константы или читать их из ноды.

### 4.4. Мёртвый код

- `guard.gd::_on_punch_area_body_entered()` не подключён ни в `guard.tscn`, ни в коде —
  единственное упоминание в проекте — само определение.
- `guard.gd`: `@export var sight_range` и `@onready var attack_area` не используются
  (обнаружение идёт через оверлап `SightArea`, чей `RectangleShape2D` 440×80 к тому же
  отцентрован по левому верхнему углу спрайта, а не по телу охранника).
- `scripts/demo/mission_demo.gd` целиком устарел (см. 2.3).
- `GameManager._on_player_died()` — пустое тело.

### 4.5. Мелочи, которые стоит поправить заодно

- `respawn(spawn_point: Vector2)` — параметр затеняет `@export var spawn_point`.
  Работает, но это классический источник путаницы, и линтер на это ругается.
- `level_01.gd` дёргает приватный метод чужого класса: `player._climb_axis()`.
- `sabotage_target.gd::_process()` переустанавливает `modulate` каждый кадр,
  `hud.gd::_process()` каждый кадр пересобирает строку инвентаря — обе величины
  меняются только по сигналам, которые уже есть в `EventBus`.
- В `player.tscn` анимация `death` использует тот же кадр 576, что и `crouch`.
  В `docs/art_saboteur93.md` это помечено как временная заглушка, но в коде пометки нет.

## 5. Инфраструктура и гигиена репозитория

- **`*.import` в `.gitignore`.** Для Godot 4 это ошибка: `.import`-файлы хранят UID
  и настройки импорта и должны быть в git. Прямое следствие уже видно в логе:
  `invalid UID: uid://bgiofmaad0ugq` в `saboteur85_tileset.tres`. UID генерируются
  заново на каждой машине, поэтому ссылки в `.tres`/`.tscn` расходятся.
- **Два `.uid`-файла не закоммичены**: `scripts/world/lift.gd.uid` и
  `assets/shaders/zx_ink_outline.gdshader.uid`. Похоже, их добавляют вручную и
  по одному (см. коммит «Track the Godot UID for the energy dial script»).
- **Пять `.pyc` в git**: `tools/saboteur_rip/__pycache__/*.cpython-312.pyc`.
  В `.gitignore` нет `__pycache__/`.
- **Абсолютные Windows-пути в коммитнутых файлах**: `C:/data/prjs/saboteur-92`
  в четырёх Lua-скриптах Aseprite, `C:\data\apps\...` в двух PowerShell-скриптах
  и в `.cursor/mcp.json`. Ни один из них не запустится на другой машине.
- **Нет манифеста зависимостей.** `README` предлагает запустить
  `python tools/generate_saboteur85_assets.py`, но Pillow нигде не объявлен —
  ни `requirements.txt`, ни `pyproject.toml`.
- **Пайплайн ассетов невоспроизводим.** Все скрипты в `tools/saboteur_rip/` читают из
  `assets/reference/original/`, а этот каталог в `.gitignore`. То есть 3000 строк
  Python-инструментов не может запустить никто, кроме владельца исходных дампов.
  Стоит хотя бы задокументировать, какие файлы туда положить.
- **Нет ни одного теста и ни одного линтера.** Для GDScript есть `gdlint`/`gdformat`,
  для логики (`GameManager`, разбор `s2_collision.json`) — GUT. Сейчас единственный
  способ заметить регрессию — запустить игру глазами.

## 6. Что сделано хорошо

Чтобы список проблем не создавал ложного впечатления — сильные стороны здесь реальные:

- **Верность оригиналу продумана на уровне констант.** `CLIMB_STEP_PX := 16.0` с
  комментарием про «одну ступеньку = одну ячейку мозаики», шаг лифта в один символьный
  ряд, привязка позы лазанья к мировому Y, чтобы кадры не «скакали» при смене
  направления, — это уже не «платформер вообще», а осознанная реконструкция.
- **Обработка лестниц заметно выше среднего.** Логика люков (`_blocking_floor_y`,
  `_blocking_ceiling_y` с проверкой продолжения перил за перекрытием) решает ровно ту
  задачу, на которой ломается большинство любительских платформеров.
- **Пайплайн вырывания ассетов серьёзный.** Извлечение из `.tap`, `.z80` и дизассемблера,
  распознавание тайлов лестниц по пиксельным паттернам (`_is_green_rail_tile`,
  `_is_x_lattice_tile`), генерация 4643 коллизий из мозаики — это большая и грамотная работа.
- **Чистая событийная развязка.** `EventBus` как автозагрузка с типизированными сигналами —
  правильный выбор, HUD не знает о `GameManager` ничего лишнего.
- **Камера в духе оригинала.** Мёртвая зона в треть экрана плюс доводка при остановке —
  разумный компромисс между flip-screen оригинала и привычной современной прокруткой.
- **Документация по арту.** `docs/art_saboteur93.md` с палитрой, картой кадров и
  QA-чеклистом — уровень, который редко встречается в хобби-проектах.

## 7. Заключение

Проект находится в состоянии **«движок готов, игры ещё нет»**, и это нормальная точка
для прототипа. Проблема в том, что сейчас он выглядит завершённее, чем есть: `README`
описывает миссию, которой нет, CI обещает APK, который никогда не собирался, а если бы
собрался — запустился бы пустым.

Разрыв между «работает у автора в редакторе» и «работает у кого-то ещё в сборке» —
это то, что нужно закрывать в первую очередь. Механика движения того стоит: она
сделана лучше, чем всё остальное вокруг неё.

### Порядок действий

Развёрнутый план с конкретными правками, критериями приёмки и проверенными рецептами —
в [`docs/remediation_plan.md`](remediation_plan.md). Ниже — краткая сводка.

**Сначала — вернуть проект в собираемое и запускаемое состояние:**

1. Убрать автозагрузку `McpBridge` из `project.godot` (2.1).
2. Перевести загрузку мира с `Image.load()` на `load()`/`ResourceLoader.exists()` (2.2).
   Это единственная правка, которая превращает сборку из пустого экрана в игру.
3. Починить триггер CI на `master` и добавить установку Android build-шаблона (2.4, 2.5).
4. Убрать `*.import` из `.gitignore`, закоммитить `.import` и оба недостающих `.uid` (5).

**Потом — сделать из этого игру:**

5. Перенести миссию на карту Saboteur II: расставить цели и охрану по вырванному миру
   вместо `_hide_demo_entities()`, либо честно убрать неиспользуемые сцены (2.3).
6. Добавить перезапуск после Game Over и экран победы/поражения (3.3).
7. Добавить кнопки «вверх»/«вниз» в `touch_controls.tscn` (3.2).
8. Решить вопрос с текстурами 8192×4608 — атлас или нарезка по экранам (3.1).

**Дальше — чтобы это не разъезжалось снова:**

9. Определиться с юридическим статусом рипов и добавить `LICENSE` (3.4).
10. Вынести лестницы и лифты из `player.gd`, свести четыре probe-функции к одной,
    заменить магические маски константами (4.1–4.3).
11. Удалить мёртвый код и устаревший `mission_demo.gd` (4.4).
12. Добавить `gdlint` в CI и `requirements.txt` для Python-инструментов (5).

## Как это проверялось

Godot `4.6.stable` (совпадает с `config/features` проекта), Linux, headless и оконный режим.

```bash
# импорт и запуск исходного проекта
godot --headless --import
godot --headless --quit-after 300

# экспорт desktop-сборки из копии проекта и сравнение доступности ассетов
godot --headless --export-debug "LinuxTest" build/test.x86_64
./build/test.x86_64 --headless --quit-after 120      # автозагрузка-проба

# воспроизведение шага CI
godot --headless --path . --export-debug "Android" exports/saboteur92.apk

# история CI
gh run list --limit 10                                # пусто
```

Пробы (`export_probe.gd`, `runtime_probe.gd`) выполнялись во временной копии проекта
в `/tmp` и в репозиторий не вносились. Полные логи приложены к ревью.
